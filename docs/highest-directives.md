## PVX 指示更正与跨视频比较方法（2026-10-17）

### 用户最新原话（逐字）

> “你理解错误 PVX指示一个视频简称 做了对比,其余视频不是PVX对比 而是类似PVX那个视频做过的对比,比较开源随便搞仓库和微软那帮傻逼研发的agent 包括不限于gpt6 效果 原话传达并不少于5000字解读 学习”

这项更正取代此前任何“每个新视频都要做一次字面上称作 PVX comparison/比较”的表述。PVX 是一个具体视频/个案的简称；其它视频可以借鉴该个案所用的证据比较方法，但不因此改名为 PVX 个案，也不继承 PVX 个案未经核验的指标或结果。

### 解读与学习（5000 字以上；以下均为操作化解释，不是用户逐字原话）

**一、先把案例名称、比较方法和比较对象分开。**“PVX”在这项更正中指向一个已经命名的特定视频个案，不是“视频比较”的通用术语，不是模型名称，不是统一基准测试套件，也不是所有未来视频的默认标签。文档、界面、工作簿、日志和报告应把 PVX 限定用于那一个案例；对其它素材使用“借鉴 PVX 案例方法的比较”“某视频的开源仓库与智能体对照”等清楚名称。名称本身必须能让读者判断正在谈哪条素材、哪项任务、哪次运行。把方法迁移到另一视频时，应先说明迁移了哪些步骤、哪些步骤因素材差异而调整、哪些评价项不能直接比较。如此既保留方法复用，也避免将一个样例的成绩扩张成对所有视频、所有模型或所有仓库的结论。PVX 是对象标签，方法是可复用程序，候选工具是被测对象；三者在数据结构中应各自有字段，不能挤进一个含糊标题。

**二、PVX 个案本身仍须按证据状态描述。**当前资料记载的是 SmartSub 3.9.0 的一份公开机器生成预览草稿，且页面明确未核实；这只证明存在该版本的草稿及其公开呈现，不证明完整输入、参数、机器型号、处理时长、质量、来源授权、音画一致、翻译准确或最终交付状态。除非找到原始运行文件、任务配置、运行日志、输出资产和审查记录，并确认它们属于同一输入与版本，否则 PVX 的任何精确成绩都应写成未知。`measured: false` 是当前记录的真实状态，不应以估值、经验、宣传文案、模型理论能力、媒体报道或另一视频的实验代替。现存预览不能自动充当真值参考；没有实际对齐的原音、字幕源文本、译文、帧样本及检查人记录，就只能说有草稿可供后续审计，不能说草稿“通过比较”或“胜出”。发现新证据时，需保留原始未知记录及证据来源，再追加有时间、版本和文件哈希的修订，不要无痕覆盖先前状态。

**三、对其它视频复用的是研究设计，不是 PVX 结果。**用户允许“类似 PVX 那个视频做过的对比”，应理解为对同类问题采用可追溯的并列比较思路，而不是复制 PVX 的视频、输入、数值、优劣排序或质量判断。每个新视频先建立自己的事件/素材标识、来源 URL、原始文件哈希、时长、画幅、语言、许可或授权状态、抽取时间范围和任务目的。随后为该素材单独建立比较记录：用同一份可用输入，或者清楚解释不同输入带来的偏差；记录每个工具从相同起点获得了什么，是否需要手动准备、模型下载、格式转换或人工编辑；留存每条路线的原始产物和可复现参数。某条路线没有运行时标为 `not_run`；只完成工程集成、没有处理媒体时标为 `engineering_only`；只有实际运行并有证据才可进入 `measured`。把方法套用于不同视频时，必须判断其语言、噪声、说话人数、剪辑、字幕位置、源清晰度和时长是否改变难度；差异不能被一个“类似 PVX”的标签抹平。

**四、被比较对象要按对象类型组织，不能混称为同一种产品。**“开源随便搞仓库”应具体落实为用户希望考察的开源项目候选，不代表已选出仓库、已检查许可证、已安装依赖或已运行。每条仓库记录至少应包含完整 `owner/repo`、主页/代码链接、被测 commit SHA、默认分支当时的解析 SHA、许可证证据及核验日期、检测出的语言和测试/媒体命令、实际执行的命令、环境限制、退出码、耗时、日志、产物路径和哈希。源仓库提供的 README 声称、CI badge 或发布说明是线索，不等于本次运行证据。若是测试仓库的测试矩阵，记录应明确它检验的是候选仓库的测试套件，不是该仓库处理 PVX 视频的效果。若是媒体处理比较，必须明确工具确实消费了相同或可比的媒体输入。开源身份也不自动表示适合本地执行、可任意下载依赖或可复制其代码；本项目只记录可验证内容，遵循适用的许可证和安全隔离流程。

**五、微软研发的 agent 也必须实名和定版后再比较。**用户希望纳入微软研发的 agent，但“微软的 agent”不是足够精确的被测对象。至少要核实产品/服务正式名称、开发或发布主体、模型供应商与模型标识、版本或部署快照、运行入口、账户/区域（若影响行为）、调用日期、会话或任务 ID、可用功能、费用或配额来源、提示词和输入资产哈希。实际体验可能由 agent orchestration、模型版本、工具、检索索引、系统提示、缓存和服务端灰度共同决定，不能把单次输出归因于未确认的模型名称。名称相似、用户猜测、论坛消息或内部昵称不构成可用 ID 的证明。若只观察到产品 UI，却无法读取模型路由，应如实写“产品路径已观察，后端模型/版本未公开或未核验”，不要反推型号。记录微软产品与开源仓库时要分别呈现对象类别、可控程度和证据可见性；差异可能来自托管配置或测量条件，并不能简单归结为谁“更聪明”。

**六、GPT-6 只能作为待核实候选，不可当成已存在且可运行的比较路线。**用户原话中的“包括不限于gpt6”表达了候选范围，不提供官方产品存在、访问权限、准确版本、API/客户端标识或实际运行的证明。只有找到可信的一手官方来源，且有可访问的具体产品/模型 ID、时间和实际调用记录，才可建立一个已确认路线。若没有这些证据，候选表中可保留 GPT-6 字样以忠实记载用户提及，但状态必须是 `unverified_candidate` 或 `not_available_for_verified_run`，不得填入虚构模型卡、性能数字、费用、推理速度、视频能力或输出。不能用相近命名、未来预测、第三方二手报道、产品宣传中的泛称或其他 GPT 版本的成绩代替 GPT-6。若之后官方资料出现，也应区分“官方宣布存在”“当前账号可访问”“本次实验成功调用”三个不同事实；任一事实都不能自动证明另外两项。候选最终不可用时，保留其未验证原因，选择已能识别的对象另行测试，并明确该替代不是 GPT-6 的代理成绩。

**七、比较应先定义研究问题，再决定任务与量尺。**“比较效果”太宽，需拆成具体可观测问题，例如字幕识别是否贴合源音、时间戳是否同步、翻译是否传达原意、字幕是否可读、渲染是否正确、操作是否可复现、资源消耗如何。一次运行不能默认覆盖所有方面。预先说明测试范围、输入来源、切片规则、语言方向、是否使用人工校订、评价者是否盲审、每项指标的定义、缺失值处理和通过门槛。若各路线接口不同，要记录如何把共同任务映射到各自接口、不可映射的能力以及可能的不公平处；不能为了得到漂亮排名而在看到结果后改变门槛。对时间戳、字符错误率、翻译、可读性、画面遮挡、运行时间、峰值内存、成本等指标分别给出定义和单位。指标适用条件不满足时用 `not_applicable`，没有观测时用 `not_measured`，运行失败时保留失败类型；这些状态不能用零、平均值或想象中的最佳值填补。

**八、要尽量控制输入和环境差异，并把无法控制的差异公开。**若比较同一视频的多个仓库或 agent，应确保素材来源、文件哈希、分辨率、音轨、裁剪区间、输入字幕、语种、提示任务和抽样位置有明确关联。若某工具只能接收 URL、另一工具必须接收文件，需记录下载/转码所引入的变化及可访问内容；若一个路线拿到全片而另一条只拿到短片，不能直接比较总处理时间或总准确率。硬件、操作系统、依赖版本、网络、缓存、并发、模型预热、限额与后台服务负载均可能影响结果，应按实际能观察的粒度记录；未观察项写未知，不伪造控制。尽可能重复运行或抽取多个代表性片段，并保留各次运行，不以最好的一次代表全部结果。若只有一次试运行，需标记为单次样本，不给出统计置信结论。若由于资源、时间或权限只能做部分测试，应公布覆盖数及缺口，避免把“运行过一些候选”写成“对比完成”。

**九、质量评估要由原始证据支撑，而不是由界面观感或模型自评支撑。**ASR 应对照可辨识的源音与有来源的人工转录，记录困难音段和不确定词；字幕同步要抽查开场、中段、结尾及快速轮换发言处的时间戳；翻译应分别核验意思、专名、数字、否定、语气和上下文；视觉审查要检查字幕位置、遮挡、截断、行数、阅读速度、颜色和帧稳定性。工具声称“准确率很高”不是独立评分，自动指标也不代表全部人类可读性。应把参考文本、对齐片段、时间码、帧截图、评价者、评分表、评判规则和争议处理方式关联到具体 run 与文件哈希。盲审、复核和多评审只有实际执行并留有记录才能如此标记；未完成的步骤不能由一段总结文字补齐。不同语言、事件与剪辑风格会改变错误分布，PVX 单例上的观察只能作为该个案结果，不能自然推广到总体。

**十、性能和成本数字必须说明测量口径。**处理速度应区分模型加载、数据准备、转码、ASR/翻译、渲染、上传和人工审阅；只报告某一步时应明确它不是总工作流耗时。成本要区分真实账单、已知计费单价乘实测用量、估算和免费额度，不应把估算说成实际支出。内存、CPU、GPU、网络和存储测量须注明采样工具、时间区间、峰值/平均值和 runner 规格；看不到服务端资源时就写不可观测。成功退出不等于结果优质，失败退出也不意味着功能必然不可用；要把运行结论与内容质量分开。所有数字需关联运行 ID、工具版本、输入哈希和日志位置，必要时提供计算脚本或原始数据表。不能因 PVX 有一项旧指标就要求其他视频使用相同单位但不同分母，也不能把人工时间漏掉后宣称某路线便宜或快。没有真实测量时保留空值或 `measured: false`，未知数字不得为了表格完整性而推估。

**十一、结果表应呈现证据等级、失败和未知，不只列胜负。**每项结论可标为“已运行且有原始证据”“部分运行”“仅代码/文档检查”“候选未运行”“不可访问”“失败”“未知”。报告需同时说明比较对象与其精确版本、输入、运行环境、原始结果、评价方法、置信限制以及复现链接。若在同一案例中有路线拿到更完整的输入或更多人工帮助，应把帮助记录为实验条件，而非隐藏差别。无输出、没有 artifact、日志缺失、仓库未检出测试入口、依赖安装失败、工具拒绝调用和纯 UI 预览是不同状态，不得合并为“没有效果”。排名只在预先声明的量尺和同等条件内成立；当各路线权衡不同，可展示多维结果而不强行得出单一冠军。将一项可验证事实和解释分开写，像“该次命令以退出码一结束”是运行事实，而“因此该项目不适合所有用户”是更广泛推论，后者需要额外证据。

**十二、学习目标是可复用的实验方法，不是预设宣传结论。**比较结束后可归纳哪些仓库结构易于复现、哪些输入要求最常导致失败、哪些质量缺陷需要人工审查、哪些输出格式便于审计、哪些 agent 功能需要更精确的路由信息。每条经验都应链接支持它的多次记录或样例，并标清是否只在某一语言/事件/版本观察到。把失败复盘转成测试用例、数据格式约定、诊断步骤或后续试验问题，避免仅留下没有出处的“某工具更好”。出现相反结果时保留反例、界定适用范围并修订经验，不要为了维护既有叙事删除旧实验。研究用工作簿或页面可以帮助浏览，但页面漂亮、信息行数多、聚合来源数量大，都不能替代输入可追溯和结果可复现。学习文档还应说明未能验证什么、要如何补证，以及哪些结论因版本变化可能过期。

**十三、实施顺序和记录结构应让审计者能从结论回到原件。**先为视频案例分配稳定 ID，再登记来源与原始资产哈希；随后登记比较计划、候选工具清单与版本解析结果；执行时每条路线生成唯一 run ID，记录云端或本地环境（依适用指示）、命令、开始结束时间、退出状态和日志；完成后保存原始输出、manifest、字幕、对齐、评分和视觉证据；最后由报告层生成对照表并指出每个结论对应哪份证据。至少区分 `case_id`、`video_id`、`repository`、`agent_product`、`model_id`、`model_version`、`run_id`、`input_sha256`、`output_sha256`、`metric_name`、`metric_value`、`evidence_uri`、`review_status` 和 `measured` 字段。无法解析的版本值应为 null 并附原因，而不是拼入展示名；未知不能因数据库约束而变成假 ID。PVX 与其它视频使用同样可审计的数据结构，但必须保有各自案例 ID 和独立结果集合。

**十四、版本变化需要建立新的证据快照。**开源仓库会更新提交，托管 agent 会更换模型路由和服务端版本，提示词、模型权重、依赖、系统镜像、服务区域和用户计划也可能变化。一次历史运行只描述该次输入与环境，不代表今天同一产品仍有同一行为。每次重跑要追加而不是覆盖旧记录，标记新旧 SHA、版本、运行日期、环境变化和可比程度；如果无法访问历史版本，报告“无法复现该版本”，不要借当前版本冒充旧版本。PVX 资料若缺少历史版本，就不能将 SmartSub 3.9.0 之外的数字推算到新版本。代理产品显示名称、模型内部代号和 API model string 可能不同，应逐项登记来源与可信级别，不能把营销系列名直接视为精确推理模型。版本未知的比较结果可保留为探索性观察，但不应进入严格的版本排名。

**十五、访问、权利、安全和资源限制也属于比较条件。**每个输入素材应记录它来自何处、是否获准处理、是否只可预览、是否允许下载、存储期限和可发布范围；这些状态与模型质量指标分开呈现。调用云端 agent 时说明所传输入是否离开仓库控制范围、是否涉及计费、数据保留和权限；没有明确授权时不得为了完成表格而调用付费接口或上传敏感文件。测试开源仓库时使用最小化检出、隔离网络和受控命令，不直接运行候选仓库自带的任意 workflow；媒体文件、依赖脚本和模型权重都可能很大，需记录空间与清理范围。安全限制导致路线未运行时，应如实标注，不把安全门槛伪装为工具能力不足，也不为赢得比较而绕过门槛。资源限制造成的未测状态说明实验覆盖受限，不可记成零性能或失败质量。

**十六、比较页面的术语应让读者不会误认为所有案例都是 PVX。**目录可设置一个“PVX 个案”卡片，旁边另列“其他视频的同方法比较”或“同方法研究案例”；两类记录使用清楚不同的案例名，并在次级说明中链接通用比较方法。每条卡片需显示素材标识、候选对象、执行状态和证据更新时间；只有实际运行的路线展示实测数值，未运行路线展示未运行原因。若某个其它视频的报告采用了 PVX 的评分框架，应写“采用 PVX 个案中使用的评价设计，并根据本视频调整”，而不是“PVX 结果”或“PVX 性能”。当页面汇总多案例时，按案例分组，不能将一个案例的评价结果复制到相邻卡片。用户明确更正的术语应该优先于旧标签；更正后对图表标题、Excel sheet 名、内部 JSON 键、网页文案和生成器说明做一致检索，避免一处改了、另一处还在宣称每个视频有 PVX comparison。

**十七、在写结论之前进行逐项覆盖核对。**检查每条路线是否记录了准确对象、是否有固定输入、是否记录实际运行状态、是否保存原始证据、是否明确评价口径、是否区分结果与解释、是否标出未知与限制。若某项不适用，应注明原因；若做不到，应明确列作未完成，不得以相似项目的公开基准补缺。对于“比较开源仓库和微软 agent 效果”的总问题，答案可能是部分完成、不同路线证据不对称或当前不能排名；这些都是有效的研究结果，只要证据充分。不能为了满足用户期待把没运行的 GPT-6、未开放的 agent 路径或只有 README 的项目写成已比较。运行失败也可产生有价值的诊断，但失败只支持对具体阶段、具体输入、具体版本的判断。最终报告应给出下一步补证计划，但将计划、实际执行和通过审查分开。

**十八、本段文字自身也不是比较证据。**上述解读把用户更正转化为执行约定，目的在于避免范围扩大、名称混淆、虚构结果和不可复现；它不证明仓库已经修改所有界面、建立完整数据库、执行任何视频处理、完成任何模型比较或产生质量结论。实施状态需要单独通过代码、云端运行、artifact、人工审阅和页面核验等证据确认。今后有新的原话或实验信息时，应保留原文、记录新增日期并清楚标示取代关系，不将操作解释冒充用户直接要求。本文不评价用户对机构或人员的措辞，也不将情绪性用语转化为产品结论；落地时聚焦可测量、可核查、可复现的任务。PVX 个案指标和 GPT-6 的正式可用性仍未知；除非取得原始证据并验证，所有汇总都应继续保持 `measured: false` 或 `unverified_candidate`，且不能宣称任何路线已经完成比较。

**十九、运行状态与证据数量必须有时间界限。**工作流的 `queued`、`in_progress`、`completed`、`cancelled` 和 `failure` 描述的是特定时刻的运行状态，不是可以脱离时间引用的永久结论。每次记录都应附上查询时间、仓库或工作流、run ID、源代码 SHA、尝试次数和状态来源；后续查询如有变化，应追加新快照并明确旧记录已被取代，不能悄悄改写过去当时确实观察到的状态。一个 workflow 显示完成，不等于所有矩阵 job 都完成；一个 job 完成，也不等于测试通过；只有结果字段、日志和实际测试命令相互吻合，才可计入相应测试结论。若 run 仍在执行，应列出已完成、活动和未开始部分，并说明当前结论不完整，而不是根据已完成的少数 job 推算最终结果。若 run 失败，要具体指出失败发生在检出、依赖安装、测试、渲染、验证或上传中的哪一步；失败阶段之后的步骤不得写成已执行。artifact 清单同样需要限定语义：文件总数可能包含错误记录、部分结果、失败日志、重复尝试或非测试输出，故必须查阅其内容和对应仓库/SHA 后再分类。没有 artifact 不能证明任务从未开始，有 artifact 也不能证明命令实际执行；仓库检出取消、测试入口不存在、测试成功、测试失败及证据上传失败是不同状态。总结覆盖率时应以目标清单为分母，对每个目标标明证据是否齐全、结果是否可判断、是否需要重跑；尚未判断的仓库不能被默认为成功或失败。重跑产生的新 artifact 需要关联新 attempt/run 标识，并保留原失败记录，以便读者区分故障是否修复。状态快照的作用是帮助监督后续工作，而不是制造完成感；当任何关键步骤或产物尚未核验时，报告必须直说未完成、未确认及下一项待核验证据。若无法及时获得最新状态，应标注最后一次查询时间，不得使用“最新”“当前”而不说明所依据的时间点。

**二十、从候选登记到比较结论要维持证据链闭环。**每个视频案例开始前，应先固定案例 ID、输入来源与文件哈希，再列出候选仓库和 agent 的选择理由；候选登记只表示计划考察，不表示已取得访问权或已经运行。执行时，为每个对象单独记录输入、版本解析、运行环境、实际命令和时间，不能把一个仓库的日志、一个 agent 的结果或同一批次其他视频的证据移作当前对象的证据。运行结束后，核对产物哈希、格式、可读取性以及它们是否对应本次 run；若只得到错误日志、空文件或不完整输出，应保留并说明其证据用途，而不能将其包装成有效结果。审核者应能从报告中的每个数字和判断追溯至具体输入、命令、源版本、日志或人工审查记录；若链接失效或文件无法访问，结论就应降级为不可独立复核。对需要人工判断的字幕正确性、翻译保真、同步和画面可读性，须保留抽样规则、参考依据、评分项和检查人；自动测试或模型自评不能替代这些审查。若不同路线的输入范围、人工帮助、等待时间或服务端能力不一致，应公开差异并限制横向推论，而不是通过删掉失败路线来制造对称。只有在预先定义的条件满足、必要证据可读且审查完成后，才能把某一维度从计划或未测状态更新为实测；否则保留 `not_run`、`partial`、`unverified` 等准确标签。每次证据更新都要说明改变了什么、基于哪一份新材料、是否影响既有结论。这样的闭环可以让后续人员重复检查、找到分歧并修正方法，也能在某项路线不可用时明确报告覆盖缺口，而不把缺口误写成优劣结果。比较的完成标准是证据和审查足以回答预先定义的问题，不是页面填满、候选数量达到目标或出现一个排名；本记录不宣称任何 PVX 或其他视频的比较已完成。
